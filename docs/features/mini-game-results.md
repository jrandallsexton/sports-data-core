# Mini-game results and stats

Status: built on `feat/mini-game-results` (2026-10-30), not yet deployed. API + migration
`AddMiniGameResult` first; the mobile half ships with the next EAS build.

## Why

Friends who playtested the football card game liked it, and one called it "quite addictive". A
record that builds over time feeds that loop. Right now a finished game leaves nothing behind.
More mini-games are planned, so the storage is generic. But it is only as generic as one game
can justify: there is one results table and no game framework.

Results are kept on the server, so they survive a reinstall or a new phone. The game itself has
to keep working offline, so results are queued on the device and uploaded once it reconnects.

The same table also tells us how the game is balanced: how often players beat the CPU, and by
how much, split by version. That is the "settle balance through play" approach (see the card
game doc's decision log) turned into numbers.

## Decisions (owner, 2026-10-30)

| # | Decision |
|---|----------|
| M1 | Results are stored server-side. The game works offline; results queue on the device and upload on reconnect. |
| M2 | Abandoned games are not recorded at all. Only games that reach a final score produce a result. |
| M3 | Stats are private for now. A leaderboard **will** follow, so nothing here may rule one out. |
| M4 | First scope: W-L-T, average margin of victory and of defeat, current and best streak, last 10 results. |
| M5 | One generic table. Game-specific detail goes in nullable jsonb until something needs to query it. |

## Data model (API database)

`MiniGameResult` (singular table name):

| Column | Type | Notes |
|--------|------|-------|
| `Id` | uuid PK | **Generated by the client** when the game ends. This is the idempotency key: a retried upload is a no-op. |
| `UserId` | uuid FK → User | Taken from the auth token, never from the request body. |
| `GameKey` | varchar(32) | `"football-cards"`. The server allows only known keys, from a constant list. |
| `Outcome` | smallint enum | Win / Loss / Tie. There is no Abandoned value (M2). |
| `Score` | int | The player's score. |
| `OpponentScore` | int | |
| `DurationSeconds` | int | |
| `GameVersion` | varchar(32) | Identifies the engine and card set, so balance numbers can be split by version. |
| `Seed` | varchar(64), nullable | The shuffle seed. The engine is deterministic apart from the shuffle, so a later "replay this game" feature is possible. |
| `Detail` | jsonb, nullable | Game-specific extras (overtime rounds, turnovers, and so on). Empty in v1. |
| `PlayedUtc` | timestamptz | When the game ended, as reported by the client (offline games upload late). |
| `CreatedUtc` | timestamptz | From `CanonicalEntityBase`: the server's receive time, from `IDateTimeProvider`. |

Index: `(UserId, GameKey, PlayedUtc)`.

`Outcome` is stored even though it could be worked out from the two scores. A future game might
not compare scores at all (a solo puzzle, for example), and storing the outcome keeps the stats
query independent of each game's rules.

**Account deletion:** `DeleteAccountCommandHandler` deletes the user's `MiniGameResult` rows.
They are private, and unlike league history no other player depends on them.

## API (new slice `Application/MiniGames/`)

`MiniGamesController`, route `user/me/minigames`, with handlers injected via `[FromServices]`:

- `POST user/me/minigames/results` takes **a batch** (`{ results: [...] }`, at most 100 items),
  because an offline device may have several queued. For each item:
  - It is inserted if its `Id` is new.
  - It is skipped if the `Id` already exists for this user.
  - It is rejected if invalid: unknown `GameKey`, negative scores, or an outcome that contradicts
    the scores for a score-compared game.
  - It is rejected once the account has stored 200 results in the past 24 hours (by server
    receive time). No real player gets near that; it bounds table growth from a scripted account.
  - A `PlayedUtc` in the future is **clamped** to server time, not rejected. A phone whose clock
    runs ahead would otherwise have every game rejected, and so lost.

  Copies of one id in the same batch collapse to its first valid copy. The response is
  `{ accepted: [...], duplicate: [...], rejected: [...] }`, and each id appears in exactly one
  list. An empty or over-100 batch, `results: null`, or a null element is a 400. The client removes **all
  three** from its queue, so a malformed item can't keep failing forever. A rejected result is
  logged with a warning (API) and reported to Sentry as a count (mobile).
- `GET user/me/minigames/{gameKey}/stats` returns raw totals instead of averages, so the client
  can merge in its queued results exactly:

```json
{
  "wins": 5, "losses": 3, "ties": 0,
  "winMarginTotal": 36, "lossMarginTotal": 17,
  "currentStreak": { "outcome": "Win", "length": 2 },
  "bestWinStreak": 3,
  "recent": [ { "id": "...", "outcome": "Win", "score": 21, "opponentScore": 14, "playedUtc": "..." } ]
}
```

`recent` holds the last 10 results, newest first. Streaks are computed in the query handler
from results ordered by `PlayedUtc`, and a tie breaks a streak. With no games, `currentStreak`
is `null`, `recent` is empty and everything else is 0. A streak's `length` is always at least 1.

## Mobile

**Queue.** When a game reaches its final score, it produces a result with
`Id = Crypto.randomUUID()` (`expo-crypto`, already a dependency). That result is appended to a
persisted queue in AsyncStorage. **Each queued item records the Firebase uid it belongs to.** A
flush only uploads items owned by the user who is currently signed in, so if someone else signs
in on the same device, their account never receives the other person's games.

**Flush triggers:**
- right after a result is queued;
- on app start;
- when `AppState` changes to `active`;
- when the stats panel opens.

There is no connectivity check and no new dependency: a flush that fails offline just leaves the
queue as it is. Only one flush runs at a time.

**Stats display.** The last server stats response is cached in AsyncStorage so the panel works on
an offline launch. What the panel shows is `merge(cachedServerStats, pendingQueue)`:
- Totals are added together.
- Queued results are newer than anything the server has, so they extend the current streak and
  the `recent` list.
- `bestWinStreak` is the larger of the server's value and the best streak in the merged
  sequence.

`merge` is a pure function with unit tests. In the uncommon case of two devices playing offline
at the same time, the merged view can be slightly off until both have uploaded, after which the
server's numbers are correct. That is acceptable.

A queued result leaves the queue only **after** the server stats that include it are cached, so
the merged view never dips between upload and refresh. If the stats refresh fails, the result
stays queued; the next upload reports it as a duplicate and clears it.

**Where it lives** (all generic, keyed by `gameKey`, except the panel):
- `src/stores/miniGameResultsStore.ts`: the queue, offline stats cache and upload.
- `src/utils/minigames/`: types plus the pure `mergeStats` / `summarize`.
- `src/hooks/useMiniGameStats.ts`: `useMiniGameStats(gameKey)` for screens, and
  `useMiniGameResultSync()`, rendered once in `app/_layout.tsx`, for the app-start and
  foreground uploads.
- `src/services/api/miniGamesApi.ts`.
- `src/components/features/cardgame/RecordPanel.tsx` on the start screen, plus a
  "Record 5-3 · Streak W2" line on the final-score prompt.

`GAME_KEY` and `GAME_VERSION` live in `src/utils/cardgame/engine.ts`. Bump `GAME_VERSION`
whenever `cards.json` or the rules change. `useCardGame` now seeds each game with
`seededRng(seed)` from a random 32-bit seed, and that seed is what gets recorded.

## Leaderboard (later, M3): what this design keeps possible

- Results already have `UserId`, `GameKey` and `GameVersion`, so a leaderboard is a query plus a
  visibility rule (global, or among league-mates). No schema change is needed.
- **Integrity is the open question.** Clients report their own results, so they can be faked.
  That is fine for private stats and probably fine for a leaderboard among friends. If anything
  of value is ever attached, the fix is to upload the seed and the action log and have the
  server re-run the game; the engine doc already plans for that. The engine is TypeScript,
  though, so server-side verification means a port or a Node sidecar. That decision waits until
  the leaderboard is built. v1 does **not** store the action log.
- The ranking metric (win percentage with a minimum number of games? margin?) is also a decision
  for the leaderboard phase.

## Out of scope for v1

- Abandons (M2).
- Per-card or per-play analytics.
- Any registry, plugin interface or per-game schema.
- Web UI. The game is mobile-only.
