ANALYSIS + REMEDIATION PLAN (Claude, 2026-09-06 morning)
=====================================================================

ROOT CAUSE (confirmed in code)
------------------------------
FootballContestEnrichmentProcessor picks the "primary" CompetitionOdds row
for the Contest-level denorm (SpreadWinnerFranchiseSeasonId / OverUnder) as:

    prefer ProviderId == SportsBook.EspnBet (58)
    else FirstOrDefault(FinalizedUtc.HasValue)   <-- arbitrary EF load order

ESPN's featured book switched to DraftKings for 2026, so EspnBet is absent
and the fallback grabs whatever loaded first. For Kent-SC that was
"DraftKings - Live Odds" (ProviderId 200, Spread NULL) -> null ATS winner
-> rendered as "Push" despite SC covering -35.5 by three touchdowns.
BaseballContestEnrichmentProcessor has the identical defect (both the
fresh-finalization and odds-late paths; four call sites total).
MatchupSqlBuilder already had the correct policy (EspnBet preferred,
DraftKings100 fallback) - which is why DISPLAYS were right all season
while FINALIZATION was a coin flip.

THE WORSE FAILURE MODE (operator's catch)
-----------------------------------------
The initial audit query only found contests where the denorm was NULL but a
provider row carried an ATS winner - i.e., visible wrong-pushes (exactly 1:
Kent-SC). That measurement was FALSE COMFORT: a live-odds row that happens
to carry a spread produces a plausible-looking, silently WRONG ATS winner
(an in-game -2.5 grades nothing like a close of -35.5). Those contests look
healthy in every null-based query. Assume any game finalized under this
code may be silently wrong, not just the null ones.

THE FIX (branch fix/odds-provider-preference, PR pending)
---------------------------------------------------------
New Application/Contests/OddsProviderPreference.SelectPrimary, used by all
four selection sites:
 1. LIVE odds rows are NEVER primary (DraftKingsLiveOdds=200,
    EspnBetLiveOdds=59). If ONLY live rows exist, SelectPrimary returns
    null and the contest-level ATS/O-U denorm is left alone - reads as
    "no line", never "push". (Deliberate: nobody should be graded against
    a line that did not exist pregame.)
 2. Ordered preference list, not single-id + arbitrary fallback:
    EspnBet(58) -> DraftKings100(100) -> DraftKings(40); unknown books fall
    back to spread-carrying-beats-spreadless.
Tests include the Kent-SC regression (order-independent), live-only ->
null, preference ordering, unfinalized exclusion.

DEFERRED (item 3 of the original report): CompetitionOdds.SpreadWinner /
MoneylineWinner are non-nullable bools mapped straight from the ESPN
payload; false-with-null-Spread is misleading. Right fix is bool -> bool?
plus migration + document processor mapping. Enrichment never reads these
columns, so deferred to its own PR rather than bundled with a grading
hotfix.

REMEDIATION PLAN (operator-directed: re-finalize the catalog)
-------------------------------------------------------------
Order of operations:
 1. Merge + deploy the fix (MUST land before tonight's NCAAFB finals -
    3 games tonight plus the Labor Day game Monday roll the same dice
    otherwise (NFL week 1 does not start until 2026-09-13)).
 2. BEFORE-SNAPSHOT: capture current denorms for the target window
    (ContestId, Name, WinnerFSId, SpreadWinnerFSId, OverUnder) so the
    post-sweep diff shows exactly which games flipped and which picks
    changed grades.
 3. SQL-clear on target contests: FinalizedUtc, AuditedUtc,
    SpreadWinnerFranchiseSeasonId, WinnerFranchiseSeasonId, OverUnder.
    SCORES STAY - they are sourced facts; this is re-DERIVATION, not the
    Idaho-style re-sourcing reenrich. EnrichOddsResults already resets
    per-row results on rerun, so reruns are safe by design.
 4. The finalization sweep re-finalizes each contest under the new policy,

 5. SCOPE: at least FinalizedUtc >= 2026-09-04 (Thu/Fri carried week-2

---------------------
- Re-scoring fires pick-result notifications again. Flipped grades: that is

POST-MERGE STATE + DETECTION RESULTS (2026-09-06, PR #732 merged)
=====================================================================

FINAL POLICY (after 3 Vortex rounds + 2 CodeRabbit rounds)
----------------------------------------------------------
OddsProviderPreference.SelectPrimary converged to:
 1. Live rows (59, 200) excluded - the ONLY pre-resolution filter.
 2. Displayed set = 58/100, compile-time DERIVED from MatchupSqlBuilder's
    constants. When any displayed row exists, resolution MIRRORS the SQL
    laterals exactly: provider order (58 first), first-existing wins,
    spread NOT considered - the denorm row is the literal row the matchup
    cards and the API pick-scoring snapshot read. If that row is
    unfinalized, ABSTAIN (null) - never substitute a row the product
    doesn't read.
 3. Historical era (no 58/100 rows at all - 10,588 contests carry spreads
    only from era books like Westgate/SugarHouse/consensus/DK40):
    fall back to any finalized non-live book, spread-carrying first, so
    historical re-finalization preserves the corpus ATS record.
 4. Null -> callers leave Contest-level fields alone ("no line", never
    "push").
Follow-up documented in both files: preferring spread WITHIN the displayed
set is a real product improvement, but it starts with the SQL laterals on
BOTH services (Producer GetMatchup*.sql + API GetMatchupResultByContestId)
and flips the policy in the SAME change. A CodeRabbit suggestion to add
provider 40 to the displayed set alone was skipped for exactly this reason
(documented on the PR).

Review-round arc, for the record: round 1 established spread-over-book;
round 2 revealed that only holds within the DISPLAYED set (10,588-contest
measurement forced the historical fallback); round 3 revealed the display
stack is provider-first, so "spread-first within displayed" contradicted
it in reverse - terminal fix mirrors the SQL literally. CodeRabbit's
finalized-gate round made the mirror pure (resolve first, gate after,
abstain on unfinalized). Invariant: GRADE AGAINST WHAT USERS SAW,
PRESERVE WHAT HISTORY RECORDED.

DETECTION RESULTS (SQL emulation of merged policy vs stored denorms)
--------------------------------------------------------------------
NCAA, remediation window (FinalizedUtc >= 2026-09-04): of 130 finalized
contests with displayed-set rows, EXACTLY 1 ATS + 1 O/U disagreement -
Kent-SC on both counts (its O/U denorm also came from the live row's 57.5
total instead of the pregame 52.5).

MLB, whole season: of 3,098 finalized contests with displayed-set rows,
24 ATS + 27 O/U disagreements (~0.8%).

The detection query lives in sql/pgsql/_remediation_odds_provider_2026_09.sql
